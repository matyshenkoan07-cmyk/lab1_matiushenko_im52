# ADR-005: Архітектура модульного моноліту та нотація UML 2.5 Component Diagram (Mermaid `classDiagram`)

- **Статус:** Прийнято
- **Дата:** 2026-11-28
- **Контекст:** Завдання 5 («Архітектура: компоненти, інтерфейси, залежності й межі системи») вимагає побудувати компонентну модель платформи онлайн-репетиторства (`TutorPlatform`), що об'єднує дані з Лаби 1 (`Student`, `Tutor`, `Subject`, `Lesson`), сценарії `UC-1..UC-4` з Лаби 2, взаємодію з Лаби 3 та процес бронювання й оплати з Лаби 4. Потрібно чітко відобразити межу системи, внутрішні модулі (`WebClient`, `APIGateway`, бізнес-сервіси, `DataAccessLayer`, `PostgreSQL`), зовнішні інтеграції (`OAuthProvider`, `PaymentGateway`, `NotificationProvider`) та стандартизовані `provided`/`required`-інтерфейси за нотацією UML 2.5.

## Decision Drivers (Критерії вибору)
- Дотримання формального стандарту UML 2.5 (офіційні стереотипи `<<component>>`, `<<interface>>`, `<<database>>`, стрілки реалізації `..|>` та залежності `..>`) без «саморобних» позначень блок-схем.
- Стабільний нативний рендеринг діаграми безпосередньо в GitHub Markdown і прозора перевірка правок у Git diff без бінарних зображень чи громіздкого XML.
- Чітке розмежування внутрішніх компонентів (`TutorPlatform`) і зовнішніх сервісів (`ExternalIntegrations`) при збереженні суворого шарування залежностей.

## Розглянуті альтернативи (Considered Options)

1. **Мікросервісна архітектура з окремими БД та брокером повідомлень (Kafka / RabbitMQ)**
   - *Плюси:* Незалежне масштабування сервісів бронювання, каталогу та оплат; повна ізоляція сховищ даних.
   - *Мінуси:* Надмірна інфраструктурна складність для поточної версії системи; розходження з єдиною реляційною схемою БД (`PostgreSQL`), спроєктованою у Лабораторній 1.

2. **Mermaid `flowchart` (`graph TD`) або експериментальний `C4Component`**
   - *Плюси:* Гнучкість у побудові довільних блоків.
   - *Мінуси:* `flowchart` не має вбудованої семантики UML (стрілки та стереотипи доводиться імітувати текстом, що порушує стандарт UML 2.5), а експериментальний `C4Component` нестабільно рендериться в нативному парсері GitHub Markdown.

3. **PlantUML Component Diagram (або зовнішній XML/SVG у draw.io)**
   - *Плюси:* Підтримка графічної нотації UML «льодяників» (`()-` / `-(`).
   - *Мінуси:* Відсутність нативного рендерингу PlantUML у GitHub Markdown без зовнішніх серверів або коміту згенерованих SVG/PNG-файлів; громіздкий XML у разі використання draw.io погіршує читабельність Git diff.

4. **Модульний моноліт із єдиною БД та стандартна нотація UML 2.5 на базі Mermaid `classDiagram` (Обрано)**
   - *Плюси:* Повна узгодженість із єдиною БД (`PostgreSQL`) з Лаби 1 та сценаріями Лаб 2–4; нативний і стабільний рендеринг у GitHub; використання канонічних UML-конструкцій: меж просторів імен (`namespace TutorPlatform` та `namespace ExternalIntegrations`), стандартних стереотипів (`<<component>>`, `<<interface>>`, `<<database>>`, `<<external system>>`), стрілок реалізації інтерфейсу (`..|>` для `provided`) та залежностей (`..>` для `required`).
   - *Мінуси:* У `classDiagram` інтерфейси відображаються у вигляді прямокутних класифікаторів зі стереотипом `<<interface>>` замість круглих символів «ball-and-socket», проте така форма є повністю валідним еквівалентом у специфікації UML 2.5.

## Рішення (Decision)

Обрано **архітектуру модульного моноліту з єдиною реляційною БД (`PostgreSQL`)** та представлення **UML 2.5 Component Diagram у синтаксисі Mermaid `classDiagram`**.

- **Чому обрано цей варіант:** Забезпечує сувору відповідність правилам нотації UML 2.5 (чіткі контракти `IAuthAPI`, `ICatalogAPI`, `IBookingAPI`, `IPaymentAPI`, `IPaymentWebhook`, `INotificationSender`, `IDataRepository` через типізовані зв'язки `..|>` та `..>`), пряме трасування до Лаб 1–4 та гарантований рендеринг безпосередньо в GitHub PR.
- **Чому відхилено мікросервіси з брокером:** Для поточної ітерації платформи розподілені транзакції, окремі БД та асинхронний брокер є надлишковими (`Out of Scope` у `spec.md`).
- **Чому відхилено `flowchart`, `C4Component` та PlantUML:** `flowchart` не відповідає формальним правилам UML, `C4Component` має проблеми з рендерингом у GitHub, а PlantUML вимагає генерації сторонніх зображень.

## Наслідки (Consequences)

- **Позитивні:**
  - Діаграма повністю відповідає специфікації UML 2.5 щодо позначення компонентів, інтерфейсів (`provided`/`required`) та меж системи (`TutorPlatform` проти `ExternalIntegrations`).
  - Досягнуто 100% узгодженості з моделлю даних (Лаба 1), Use Cases (Лаба 2), Sequence-діаграмою (Лаба 3) та Activity-діаграмою (Лаба 4).
- **Обмеження та компроміси:**
  - Кешування (`Redis`), CDN та брокер повідомлень свідомо виключені з поточної версії (`AC-5`), але ізоляція бізнес-мо
