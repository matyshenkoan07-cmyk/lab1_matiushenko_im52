# ADR-005: Архітектура модульного моноліту та нотація UML Component Diagram (Mermaid)

- **Статус:** Прийнято
- **Дата:** 2026-11-16
- **Контекст:** Завдання 5 («Архітектура: компоненти, інтерфейси, залежності й межі системи») вимагає побудувати компонентну модель платформи онлайн-репетиторства (`TutorPlatform`), що об'єднує дані з Лаби 1 (`Student`, `Tutor`, `Subject`, `Lesson`), сценарії `UC-1..UC-4` з Лаби 2, взаємодію з Лаби 3 та процес бронювання й оплати з Лаби 4. Потрібно чітко відобразити межу системи, внутрішні модулі (`UI`, `API Gateway`, бізнес-сервіси, `DataAccessLayer`, `PostgreSQL`), зовнішні інтеграції (`OAuthProvider`, `PaymentGateway`, `NotificationProvider`) та `provided`/`required`-інтерфейси.

## Decision Drivers (Критерії вибору)
- Прозора перевірка змін (Git diff) і нативний рендеринг діаграми безпосередньо в GitHub Markdown без збереження бінарних зображень або громіздкого XML.
- Чітке розмежування внутрішніх компонентів (`TutorPlatform`) і зовнішніх сервісів (`Out of Boundary`) із явним відображенням `provided` та `required` інтерфейсів.
- Збереження суворого шарування залежностей (відсутність прямих звернень UI або сервісів до бази даних) без надмірного ускладнення інфраструктури брокерами повідомлень чи кешем на поточній ітерації.

## Розглянуті альтернативи (Considered Options)

1. **Мікросервісна архітектура з окремими БД та брокером повідомлень (Kafka / RabbitMQ)**
   - *Плюси:* Незалежне масштабування сервісів бронювання, каталогу та оплат; повна ізоляція сховищ даних.
   - *Мінуси:* Надмірна інфраструктурна складність для поточної версії системи; розходження з єдиною реляційною схемою БД (`PostgreSQL`), спроєктованою у Лабораторній 1.

2. **PlantUML Component Diagram (або зовнішній XML/SVG у draw.io)**
   - *Плюси:* Стандартна нотація UML «льодяників» (`()-` / `-(`) для `provided`/`required` інтерфейсів.
   - *Мінуси:* Відсутність нативного рендерингу PlantUML у стандартному GitHub Markdown без зовнішніх серверів або коміту згенерованих SVG/PNG-файлів; великий XML-код у разі використання draw.io ускладнює рев'ю в Git diff.

3. **Модульний моноліт із єдиною БД та декларативною діаграмою в Mermaid `flowchart` (Обрано)**
   - *Плюси:* Повна узгодженість із єдиною базою даних (`PostgreSQL`) з Лаби 1 та сценаріями Лаб 2–4; нативний рендеринг у GitHub; чистий текстовий diff у комітах; наочне групування межі системи (`subgraph TutorPlatform`), виділення овальних вузлів інтерфейсів (`«interface»`) та розділення суцільних зв'язків реалізації (`provided`) і пунктирних залежностей (`required`).
   - *Мінуси:* Mermaid `flowchart` не має вбудованих напівкруглих символів «socket» для `required`-інтерфейсів, тому вони позначаються стереотипом `«interface»` і підписами `required` на пунктирних стрілках.

## Рішення (Decision)

Обрано **архітектуру модульного моноліту з єдиною реляційною БД (`PostgreSQL`)** та декларативне представлення **UML Component Diagram у синтаксисі Mermaid `flowchart`**.

- **Чому обрано цей варіант:** Забезпечує пряме трасування до всіх попередніх лабораторних робіт (спільна схема БД у `DataAccessLayer`, чіткі контракти `IAuthAPI`, `ICatalogAPI`, `IBookingAPI`, `IPaymentAPI`, `IPaymentWebhook`, `INotificationSender`, `IDataRepository`), а також дозволяє рев'юеру переглядати рендер і історію комітів безпосередньо в GitHub PR.
- **Чому відхилено мікросервіси з брокером:** Для навчальної ітерації платформи розподілені транзакції, окремі бази даних та асинхронний брокер є надлишковими (`Out of Scope` у `spec.md`).
- **Чому відхилено PlantUML / draw.io:** Вимагає додаткової генерації зображень або коміту громіздкого XML, що погіршує читабельність історії правок у репозиторії.

## Наслідки (Consequences)

- **Позитивні:**
  - Досягнуто 100% узгодженості архітектури з моделлю даних (Лаба 1), Use Cases (Лаба 2), Sequence-діаграмою (Лаба 3) та Activity-діаграмою (Лаба 4).
  - Усі залежності проходять через визначені інтерфейси (`provided`/`required`), а зовнішні сервіси (`OAuthProvider`, `PaymentGateway`, `NotificationProvider`) чітко винесені за межу `TutorPlatform`.
- **Обмеження та компроміси:**
  - Кешування (`Redis`), CDN та брокер повідомлень свідомо виключені з поточної версії (`AC-5`), але чітке виділення інтерфейсів (`IPaymentAPI`, `INotificationSender`, `IDataRepository`) дозволяє в майбутньому винести будь-який сервіс окремо без зміни бізнес-логіки.
