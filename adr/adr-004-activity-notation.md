# ADR-004: Вибір нотації Activity-діаграми (Mermaid flowchart) для моделювання процесу бронювання та оплати

- **Статус:** Прийнято
- **Дата:** 2026-11-16
- **Контекст:** Завдання 4 («Процес / поведінка») вимагає змоделювати динамічний бізнес-процес бронювання та оплати заняття (`UC-2` + `UC-4`) за участю кількох сторін (`Student`, `BookingService`, `PaymentService`), з урахуванням розгалужень, паралельних дій, асинхронних повідомлень (`Webhook`, сповіщення) та події тайм-ауту.

## Розглянуті альтернативи

1. **Машина станів (`stateDiagram-v2` у Mermaid)**
   - *Плюси:* Добре відображає життєвий цикл та переходи станів однієї сутності (`Lesson`: `Available` → `Pending_Payment` → `Confirmed`).
   - *Мінуси:* Не підтримує розбиття на доріжки учасників (Swimlanes), не дозволяє явно показати паралельне виконання (`fork`/`join`) та обмін повідомленнями між різними сервісами.

2. **BPMN 2.0 (через зовнішній XML / SVG з draw.io)**
   - *Плюси:* Повна підтримка стандартних подій часу, повідомлень та пулів/доріжок.
   - *Мінуси:* Складність рев'ю в Git diff (великий згенерований XML або бінарний файл), відсутність нативного текстового редагування без сторонніх редакторів.

3. **Activity-діаграма у синтаксисі Mermaid `flowchart` (`graph TD`)**
   - *Плюси:* Нативний рендеринг безпосередньо в GitHub Markdown, прозорий текстовий diff у комітах, підтримка групування за учасниками (`subgraph`), явне відображення смуг синхронізації (`FORK`/`JOIN`), подій часу та передачі повідомлень (`send`/`accept`).
   - *Мінуси:* Потребує суворого дотримання правил вкладеності вузлів у `subgraph` для коректного візуального розміщення.

## Рішення

Обрано **Activity-діаграму у нотації Mermaid `flowchart` (`graph TD`)**.

- **Чому обрано цей варіант:** Дає змогу поєднати нативний рендеринг у GitHub із повним контролем над розподілом відповідальності між 3 учасниками, чітко відобразити смуги синхронізації (`FORK`/`JOIN`), незалежний тайм-аут оплати та події обміну повідомленнями (`send`/`accept`), зберігаючи прозору історію змін у Git.
- **Чому відхилено машину станів (`stateDiagram-v2`):** Вона фокусується лише на зміні станів одного об'єкта (`Lesson`) і не здатна показати, який саме сервіс чи актор виконує дію, а також не підтримує міжсервісні повідомлення та паралельні гілки.
- **Чому відхилено BPMN 2.0 (draw.io / XML):** Візуальні редактори генерують громіздкий XML-код, у якому неможливо зручно відстежувати точкові виправлення в комітах (Git diff), що ускладнює аудит змін порівняно з текстовим синтаксисом Mermaid.

## Наслідки

- **Позитивні:** Процес чітко розподілений між 3 відповідальними учасниками (`Student`, `BookingService`, `PaymentService`), наочно показано асинхронну взаємодію через `send`/`accept`, незалежний тайм-аут на 15 хвилин та паралельне підтвердження запису й надсилання сповіщення.
- **Обмеження:** Технічні деталі збереження даних (`Database`) та проміжний шар `ClientUI` інкапсульовані всередині `BookingService`, щоб не перевантажувати бізнес-процес.
