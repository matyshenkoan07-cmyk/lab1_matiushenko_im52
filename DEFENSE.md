DEFENSE — Завдання 3: Взаємодія (Sequence)

Намір і критерії (1–2 речення):
Було розроблено Sequence-діаграму у синтаксисі Mermaid та текстову специфікацію spec.md для деталізації динаміки взаємодії компонентів у сценарії бронювання та оплати занять (UC-2 + UC-4). 
Критерії: у сценарії присутній один актор-людина (Учень), відокремлені мікросервіси (BookingService, PaymentService) та база даних. Описано основний потік, розгалуження alt/else для успішної та невдалої оплати зі зміною статусів уроку, а також блок opt для надсилання сповіщень. 


Початково на діаграмі платіжний шлюз було додано як зовнішнього актора UML, що порушувало канони моделювання. При виправленні платіжну систему було переведено у статус внутрішнього сервісу PaymentService, залишивши актором лише Учня. 
            Коміт: fix: remove external payment gateway actor from sequence diagram. 

Підписи відповідей від бази даних та назви умовних блоків містили суміш англійських та українських слів. При виправленні всі текстові підписи та відповіді було переведено на чисту українську мову, залишивши англійською лише назви методів у camelCase. 
Коміт: fix: translate sequence diagram labels to pure Ukrainian. 

При помилці оплати або затримці з'єднання статус замовлення в базі даних залишався Pending_Payment, що блокувало слот. При виправленні додано чіткий виклик updateLessonStatus зі зміною статусу на Available для повернення слоту в розклад.
Коміт: fix: update lesson status to Available on payment failure. 

Ключове рішення — які альтернативи зважив і чому обрав цю (ADR):
Розглядалися дві альтернативи архітектурної обробки платежу:
Синхронний варіант: тримати з'єднання та очікувати відповіді банку безпосередньо у BookingService.
Асинхронний варіант (обрано): виділити окремий PaymentService, який ініціює платіж, повертає посилання учню та обробляє результат через Webhook callback. Монолітний/синхронний варіант було відхилено через ризик зависання потоків при затримках платіжного шлюзу. Обраний асинхронний варіант дозволяє створювати чернетку уроку зі статусом Pending_Payment і гнучко обробляти повернення слоту в стан Available у разі відмови.
